# Подписки на котировки — BlockingQueue и ExecutorService

Цель самостоятельной работы после семинара — заменить механизм исполнения подписок,
сохранив команды `watch`, `remove`, `exit`, интервалы после ответа и отмену запроса.
На занятии решаются `SynchronizationExercises` и `ExecutorExercises`.

## Запуск готовых вариантов

Из корня поднять mock-server и запустить приложение с прерываемым клиентом.
Main-класс проекта — `academy.backend.market_pulse.Main`.

```bash
docker compose -f docker/mockserver/docker-compose.yml up -d
MARKET_PULSE_CLIENT=HTTP_CLIENT java -cp <classpath> academy.backend.market_pulse.Main subscriptions --engine treiber --workers 3
```

Для сравнения заменить `treiber` на `queue` или `executor`. Default — `executor`.
Команды вводятся в консоли одного запущенного процесса.

```text
watch SBER 3s 30s
watch GAZP 5s 1m
remove SBER
exit
```

Для проверки отмены медленного ответа задать `MARKET_PULSE_MOCK_SCENARIO=timeout`.

## Этап 1. Стек → BlockingQueue

В `QueueThreadPool` вместо `TreiberStack` используется `LinkedBlockingQueue`.
`take` ожидает задачу, `add` публикует её для consumer. Потребность в ручном `unpark` исчезает.
Очередь неограниченная, как исходный стек. Перегрузка bounded executor отдельно показывается
в `ExecutorFrameworkDemoTest.boundedPoolRejectsOverload`.

Общий `TaskPool` содержит `submit` и `close`. Команды по-прежнему обрабатывает
`QuoteSubscriptionService`, с теми же `SubscriptionRequest`, `SubscriptionResult` и контрактом клиента.
FIFO описывает порядок извлечения ожидающих задач. При нескольких worker запросы могут
завершаться в другом порядке.

## Этап 2. Стандартные executor и Future

Сравнить исходный сервис с `ExecutorQuoteSubscriptionService`.
Scheduler назначает следующий запуск, а `newFixedThreadPool` выполняет HTTP-запросы.
Следующий запуск назначается после завершения предыдущего запроса, без перекрытия HTTP одного тикера.

В `dispatch` FutureTask сохраняется до `workers.execute` под монитором конкретной подписки.
Поэтому `remove` видит задачу, которая ещё ждёт worker, и может вызвать `cancel(true)`.
Состояние `running` хранится отдельно от статуса Future. Future становится cancelled сразу,
а кооперативное завершение кода запроса может занять время.

Общий `QuoteSubscriptions` сохраняет DTO, `SubscriptionResultHandler` и отдельный `onTaskFailure`.
Консольный формат остаётся в `SubscriptionsCommand.formatResult`.

## Что проверить

- `remove SBER` прерывает запрос SBER, другие подписки продолжают работать.
- Отменённая задача в очереди не начинает HTTP-запрос и не публикует результат.
- Истёкшая queued-задача освобождает тикер для нового `watch`.
- Выполняющийся запрос удерживает тикер до завершения, повторный `watch` отклоняется.
- Callback разных тикеров могут выполняться одновременно, `remove` ждёт начавшуюся публикацию своего тикера.
- Ошибка callback попадает в `onTaskFailure` и не вызывает повторную публикацию через тот же callback.
- `exit` возвращается после завершения scheduler и worker-потоков.

Контрактные проверки применяются ко всем трём engine в `QuoteSubscriptionServiceTest`.
Реальный прерываемый HTTP проверяется в `SubscriptionHttpTest`. Тест `QueuePoolTest`
проверяет FIFO и сохранность задач при конкурентных producer.
